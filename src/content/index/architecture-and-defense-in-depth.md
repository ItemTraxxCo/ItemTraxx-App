## Overview & System Architecture

Modern enterprise inventory and asset tracking platforms routinely make the critical mistake of co-locating authentication, ingestion, and persistent storage inside a single perimeter. In educational technology, this architectural shortcut creates a large blast radius: a single misconfigured access policy or compromised service token exposes sensitive student records, equipment custody histories, and organizational identity data. ItemTraxx was designed from the start to avoid perimeter-based trust. Instead, the system treats every tier, from the edge entrypoint down to the persistent database storage, as an untrusted boundary operating under defense-in-depth principles. Decoupling ingress routing, identity authority, and cryptographic operations is designed so that compromising a single subsystem does not expose plaintext data on its own

The ingress perimeter is anchored by an isolated edge proxy distributed across global point-of-presence infrastructure. Rather than permitting client browsers to interface directly with application databases or internal services, every inbound connection terminates at the edge. At this perimeter, strict origin verification enforces an immediate deny-by-default posture against unverified domains before application compute ever spins up. Inbound mutation traffic is systematically scrubbed and required to present verified edge protocol headers, neutralizing cross-site execution and ambient browser request vulnerabilities. Complementing this structural hardening, tiered rate limiters protect session exchanges, token refreshes, and public verification funnels against credential stuffing. Edge-level circuit breakers, covered in the Zero Trust section below, handle isolation during incident response

Identity and session authority operate in complete isolation from standard application data. The browser client maintains a strictly stateless security posture: no long-lived API tokens, bearer credentials, or raw cryptographic tokens ever enter client-side storage where malicious extensions or cross-site scripting vulnerabilities could harvest them. Authentication state is mediated entirely through secure, HTTP-only, SameSite cookies. Behind the edge proxy, a dual-layer session engine cross-references active requests against a real-time database session registry. This overlay ensures that session revocation, workspace suspension, or device anomalies terminate access instantly rather than waiting for token expiration. For privileged operations, the platform mandates time-bounded cryptographic re-authentication via WebAuthn, ensuring high-impact actions cannot be executed from stale or hijacked sessions

The persistent storage tier enforces least-privilege access by design. Within the database engine, direct write privileges across core operational entities are completely revoked from client roles; all state mutations must execute through isolated, idempotent edge runtimes or atomic database procedures that enforce strict tenancy boundaries. Most crucially, storage authority is decoupled from decryption authority. The core database operates exclusively over authenticated ciphertext, nonces, and one-way cryptographic indexes. Workspace-specific Data Encryption Keys reside solely in ephemeral memory within an isolated cryptographic service, protected under an overarching Key Management hierarchy. By isolating keys from persistent storage, rotating or purging a workspace key instantly executes cryptographic shredding across all live records and immutable backups, supporting data-disposal requirements without manual database cleanup

## Row-Level Security & Postgres Isolation

The conventional approach to multi-tenant application security relies almost exclusively on application-level filtering: queries append a tenant identifier in the WHERE clause, trusting that every developer, ORM query builder, and edge route consistently enforces the boundary. In practice, this design is a common cause of multi-tenant data breaches. A single unindexed query, an omitted parameter, or an unchecked edge handler silently leaks records across organizational borders. ItemTraxx eliminates this failure mode by delegating all tenancy enforcement down to the database engine itself through comprehensive Row-Level Security (RLS) policies implemented in PostgreSQL. Tenancy boundaries are enforced by the database on every query rather than left to application code.

Under the ItemTraxx database posture, direct client access is constrained through strict privilege revocation. Standard authenticated roles are granted zero direct mutation capabilities on core operational tables. Any attempt by a client session to issue direct INSERT, UPDATE, or DELETE statements on sensitive entities fails immediately at the permission layer, preventing compromised client credentials or exploited REST surfaces from altering system state. State transitions execute exclusively through atomic database procedures operating under explicit definer security boundaries or through privileged, sandboxed edge services. These procedures act as transactional gates, validating caller identity, tenancy context, and state preconditions before executing mutations within an isolated transaction.

Tenancy boundaries within the database are anchored to cryptographically verified workspace identifiers derived from active session context. Access policies evaluate every row against the calling principal's verified workspace membership, isolating school districts, campuses, and independent organizations from one another. Administrative principals are strictly scoped to the boundaries of their specific workspace tenancy, while standard member accounts are further restricted through granular grant policies that only surface resources explicitly assigned or designated for global workspace visibility. The underlying authentication schema is isolated entirely from public and authenticated client roles, ensuring that identity internals, credential hashes, and session authority tables cannot be queried through application endpoints

To safeguard historical integrity, ItemTraxx enforces append-only custody and audit logs directly at the storage layer. Every asset checkout, return, status transition, and administrative intervention generates an immutable audit record tied to the executing principal and workspace boundary. These records cannot be modified or truncated by application roles, establishing a tamper-evident audit trail that provides a clear record of equipment chain of custody. By pairing pervasive Row-Level Security with the complete revocation of direct client write grants, the persistent storage tier is designed to keep tenants isolated even if an upstream application runtime is compromised

## Upstream Dependency Management & CVE Hotfix Pipeline

Modern cloud infrastructure is inherently vulnerable to supply-chain risk. A secure application layer means very little if upstream packages introduce transitive vulnerabilities, supply-chain poisoning, or zero-day exploits into the build pipeline. ItemTraxx approaches dependency security through continuous telemetry, multi-source vulnerability intelligence, and an isolated, multi-stage remediation lifecycle. Rather than treating dependencies as trusted, static components, the codebase subject them to automated auditing that intercepts security alerts before they can reach production artifacts.

Vulnerability ingestion is anchored across automated scanning platforms and real-time advisory databases. The development and deployment infrastructure ingests telemetry from the [GitHub Advisory Database](https://docs.github.com/en/code-security/concepts/vulnerability-reporting-and-management/github-advisory-database) alongside continuous security analysis from our security provider, [Aikido Security](https://www.aikido.dev/). Automated monitors track both direct application libraries and transitive dependencies across the entire runtime hierarchy, live code, and deployed artifacts. When an advisory or Common Vulnerabilities and Exposures (CVE) identifier is published, automated monitors evaluate the dependency tree immediately, triaging the vulnerability against the live codebase to determine actual exploitability, package reachability, and severity tiering. 

When an upstream advisory is confirmed reachable in our codebase, remediation follows a strict verification pipeline rather than unvetted automated upgrades. We conduct an upstream source audit, reviewing the specific patch diffs and commit histories from the upstream maintainers to verify the integrity and completeness of the fix. Once the patch is integrated, the remediation enters an isolated local test harness to ensure state transitions, security boundary rules, and existing functionality and security remain intact. The update is then deployed to our staging environment for integration testing across isolated infrastructure, followed by deployment to a production-parity preview environment for end-to-end regression testing. Only after passing all staging and preview checkpoints is the pull request merged into main, triggering automated continuous deployment that distributes the verified, hardened release to production users globally. 

## Zero Trust Access & Perimeter Defense

Traditional enterprise software often relies on castle-and-moat security: once traffic passes an outer firewall, it is trusted. In educational and organizational environments, that assumption does not hold up. ItemTraxx grants no request implicit trust, internal or external. The edge perimeter described in the overview, with its origin validation, mutation intent headers, tiered rate limits, and cookie-only sessions, applies to every request, and no client ever talks to the database directly.

That perimeter matters most during an incident. The edge includes distributed circuit-breaker controls that let us isolate specific API surfaces, throttle affected ingress routes, or put targeted parts of the platform into maintenance mode within seconds. Because these controls live at the edge rather than in application code, emergency mitigation does not wait on a new deployment, and suspicious activity can be contained at the network boundary before it reaches downstream services, tenant data, or our customers.
