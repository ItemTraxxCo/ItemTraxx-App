# Workspace borrower envelope encryption: design and implementation plan

Status: proposed for approval. Project P-ITX-10.

## Goal and boundary

Protect borrower names, external borrower IDs, and email addresses at rest in Supabase/Postgres. The browser talks only to the existing edge API; Supabase Edge Functions and the Cloudflare security gateway (SGW) are trusted to process plaintext. This is server-mediated encryption, not end-to-end encryption or zero knowledge against trusted compute. Workspace UUIDs and internal borrower UUIDs remain relational identifiers, not external borrower IDs.

Each workspace has an independent AES-256-GCM data encryption key (DEK) and HMAC-SHA256 pepper. Cloudflare KV stores only the encrypted key material; the SGW holds a 256-bit KEK and an internal authentication secret as Cloudflare secrets. No wrapped DEK or pepper is stored in Postgres or returned to callers. Key material and PII must never enter logs, URLs, analytics, error responses, or telemetry.

## Architecture choices and guarantees

The requested choice is Cloudflare KV rather than Durable Objects. KV is eventually consistent: reads, including negative reads and deletion visibility, can lag for 60 seconds or longer. Revocation is therefore not instantaneous; after propagation, the SGW must refuse use of a revoked key. Existing offline packs and already disclosed data cannot be revoked remotely. KV deletion alone does not establish physical erasure from Cloudflare retention, replicas, exports, or other copies. Document and verify provider retention and backups; do not promise irreversible destruction until all key copies and old plaintext backups are accounted for. Rotation that preserves access must decrypt and re-encrypt before retiring the old key. Destructive key deletion is a separate, explicitly controlled operation.

A KV get-then-put check is not atomic: simultaneous first-time creators can both observe absence and overwrite one another. Use the requested check as a defensive validation, but never rely on it to serialize creation. Provision keys through a controlled single-writer provisioning process with durable, workspace-scoped state in Postgres containing no keys; crypto operations fail closed until provisioning is confirmed. If provisioning has an ambiguous outcome, stop and reconcile the existing KV entry; never automatically replace it. Define and test a concurrency-safe claim and recovery procedure before enabling automatic provisioning. A key may only be created for an explicitly new workspace, never as a fallback for a missing key on an existing workspace or after revocation. A PostgreSQL coordination record does not contain key material and must not let a restored database reactivate a shredded key.

## Gateway

Create `cloudflare/sgw` as a separately deployed Worker named `itemtraxx-sgw`, routed to `sgw.itemtraxx.com/*`, and a dedicated KV namespace in the specified Cloudflare account through Safari. Bind the namespace and configure secrets without committing or printing them. Provisioning, revocation, configuration, and release steps must be auditable and use least privilege. The gateway accepts only authenticated server-to-server POSTs, denies browser CORS, checks request size and schema, verifies bearer credentials safely, returns generic errors, and never exposes keys. Establish rate limits and operational monitoring without capturing request bodies. A public route with a shared secret is not itself a private network boundary.

Expose authenticated key provisioning, encrypt, batch decrypt, blind-index, and controlled revoke operations. They accept a workspace UUID; callers do not supply wrapped keys. Use Web Crypto, random 256-bit DEKs and peppers, fresh 96-bit AES-GCM nonces, 128-bit tags, and a documented versioned base64 envelope. Bind workspace UUID, purpose, envelope version, and key version as authenticated additional data for wrapping and payload encryption. Bind borrower UUID where available so ciphertext cannot be moved between records. Separate HMAC domains for borrower ID and email, normalize with trim and lowercase consistently, and document exact Unicode behavior. Limit input and batch sizes. Fail the whole batch without returning partial plaintext on authentication failure. Keep key versions explicit; implement KEK rewrapping and DEK rotation as distinct audited procedures.

## Data and authorization

Add nullable encrypted payload, nonce, tag, key version and workspace-scoped blind-index columns first. Preserve existing rows during the backfill. Add indexes and enforce uniqueness for active borrower IDs according to current product semantics after detecting normalization collisions. Verify email collision behavior before imposing uniqueness. Keep internal UUID foreign keys and workspace/access grants intact. Maintain atomic creation of borrower and grants through a revised service-role-only transaction/RPC using ciphertext and hashes, not raw PII. Review all RLS, grants, views, triggers, functions, audit tables and SQL constraints before removing plaintext columns. Never introduce a tenant key table in Postgres.

Authorization remains enforced by the existing Better Auth, trusted ingress, workspace access, device session and borrower-grant checks. Resolve workspace from authenticated server context and verify each requested borrower belongs to that workspace and is accessible before decrypting. Super-admin paths must keep their existing explicit authorization; cross-workspace decryption must not be exposed to ordinary users. Directory responses use bounded pagination/batches and no shared persistent plaintext cache.

## Staged application changes

1. Inventory every borrower PII read/write and copy, including direct authenticated PostgREST, service-role functions, SQL routines, exports/imports, super-admin views, audit/security logs, analytics, offline packs, tests, and historical migrations. Current confirmed examples include `src/services/borrowerService.ts`, `checkout-borrower-lookup`, `checkoutReturn`, `offline-checkout`, `admin-borrower-mutate`, and `super-borrower-mutate`. Distinguish external `borrower_id` from UUID foreign keys of the same name.
2. Deploy and validate the gateway and additive schema without dropping legacy columns. During rollout, restrict access and prevent unencrypted new writes before claiming zero PII. Establish a maintenance window or equivalent writer freeze for the final backfill and cutover; dual-write plaintext cannot meet the final guarantee.
3. Provision workspace keys using the coordinated workflow. Run an idempotent, resumable, rate-limited backfill through trusted compute, encrypting existing `username` and external `borrower_id` as name/display data and ID, with optional email where present. Record progress without PII; verify counts, decryptability, indices, authorization, and normalization collisions. Do not log plaintext or silently skip failed rows. Existing generated usernames must remain available as display names until deliberately changed.
4. Route list, exact lookup, create, bulk import, archive/restore and privileged reads through authenticated Edge Functions. For checkout, hash the scanned external ID, select by workspace and blind index, authorize the borrower, and decrypt only what is needed. Update checkout and return together. For offline pack creation and refresh, decrypt authorized borrower data in trusted compute before sending it to the client; preserve UUID cursor, grant and expiry semantics. Existing encrypted device-side packs may contain plaintext after local decryption; verify their retention and revocation behavior and do not represent them as covered by KV shredding.
5. Add single-name and split-name modes, optional email, and freeform external IDs respecting existing maximum length. Support in-memory directory filtering by display name, ID and email; exact barcode lookup uses the broker. Preserve bulk imports, accessibility, loading/error states and existing access controls. Clear in-memory data on session/workspace change and logout.
6. Cut over only after all rows and paths are verified, older application versions and jobs can no longer write plaintext, and rollback has been reviewed. Remove or null legacy plaintext columns and remove plaintext-dependent RPCs, views, constraints, indexes and log fields. Enforce non-null ciphertext and index fields once verified. Nulling/dropping columns does not remove values from old backups, WAL, logs, exports or provider retention; inventory and address each separately.

## Validation and release gates

- Unit tests: key wrapping, independent workspace keys, AES-GCM round trips, tampering and cross-workspace/record substitution rejection, domain-separated deterministic HMAC and normalization, malformed input, missing/revoked keys, wrong secret, and bounded batches.
- Concurrency and recovery tests: parallel provisioning cannot produce multiple accepted keys; ambiguous KV writes, delayed and negative reads, revocation, interrupted backfills, duplicate IDs, rotation and retry fail safely without overwriting keys or losing data.
- Integration tests against real authorization and database enforcement: no plaintext fields in Postgres writes, SQL routines, logs or telemetry; isolation and grants hold across list, exact lookup and privileged paths; checkout, return, offline pack build/sync and archive/restore work before and after cutover. Test malicious substitution and clean failures without leaking plaintext.
- Rehearse migration on representative non-production data, verify source-to-encrypted counts and decryptability, test rollback at each stage, and inspect deployed Worker, route, KV binding, secrets presence and health. A staging test does not prove production is migrated or that existing backups are clean.
- Confirm actual Cloudflare deletion propagation and provider retention policy; document limits. Verify cleanup and key-destruction runbooks independently before claiming shredding.

## Execution sequence

After approval: finish repository-wide inventory and implement gateway and focused tests; add schema and broker with authorization tests; implement backfill and rollout controls; update all borrower, checkout and offline paths and UI; run full relevant verification and staging rehearsal; then prepare production migration/deployment and dashboard configuration for review. Do not silently perform destructive key deletion or plaintext cleanup while data migration and recovery have not been verified.
